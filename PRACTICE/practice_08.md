## 2. Аналіз та Декомпозиція

В рамках практичної роботи №8 було реалізовано механізм абстракції бізнес-логіки через створення кастомних хуків. Це дозволило відокремити логіку взаємодії з браузерними API від візуальної логіки компонентів.

### Реалізовані кастомні хуки:

1.  **`useWindowSize`**:
    - Відстежує зміни розмірів вікна браузера (`resize`).
    - Використовує `useEffect` з функцією очищення `removeEventListener`.
    - Дозволяє компонентам адаптуватися до мобільних пристроїв (наприклад, у `Practice8.jsx`).
2.  **`useOnlineStatus`**:
    - Моніторить стан підключення до мережі (`online`/`offline`).
    - Додатково відстежує тип з'єднання (4g, 3g тощо) через `navigator.connection`.
    - Використовується в `App.jsx` для відображення глобального статусу мережі.
3.  **`useThemeContext`**:
    - Керує станом теми (світла/темна).
    - Синхронізує обрану тему з `localStorage` для збереження стану після перезавантаження.
    - Автоматично оновлює атрибут `data-theme` на кореневому елементі `html` для глобальної зміни стилів.

### Результати:
- Код компонентів став чистішим завдяки винесенню `useEffect` та обробників подій.
- Реалізовано глобальну систему тем, яка працює на рівні всього `body`.
- Додаток став більш відгукливим на зміни стану мережі та розмірів вікна.

## 3. Контрольні запитання

1. **Яке єдине та головне синтаксичне правило накладає React на функції, які розробник хоче ідентифікувати як "Кастомний хук" (Custom Hook), і чому порушення цього правила викликає помилку лінтера (ESLint)?**
   - Назва кастомного хука обов'язково повинна починатися з префікса `use` (наприклад, `useWindowSize`). Це правило дозволяє ESLint-плагіну `eslint-plugin-react-hooks` автоматично перевіряти дотримання правил хуків (наприклад, їх не можна викликати всередині циклів або умов).

2. **Чи ділять між собою спільний (однаковий) стан windowSize (пам'ять) два різні компоненти, якщо вони обидва викликали всередині себе useWindowSize()? (Поясніть, хук це інстанс чи виклик функції).**
   - Ні, вони не ділять стан. Кожен виклик хука — це незалежний виклик функції, який створює власний набір станів (`useState`) та ефектів (`useEffect`) всередині конкретного компонента. Хук — це спосіб перевикористання *логіки*, а не *даних*.

3. **При створенні useOnlineStatus, чому ми використовували саме масив залежностей [] для useEffect? Що сталося б, якби ми взагалі не передали другий аргумент в useEffect?**
   - Порожній масив `[]` означає, що ефект виконається лише один раз при монтуванні (підписка) та один раз при розмонтуванні (відписка). Якби ми не передали масив, підписки створювалися б при кожному рендері компонента, що призвело б до витоків пам'яті та зайвого навантаження.

4. **В чому полягає критична небезпека відсутності функції очищення (у команді return () => window.removeEventListener(...)) всередині хука windowSize, якщо компонент-споживач (наприклад, сторінка налаштувань) постійно монтується і розмонтовується під час навігації користувача?**
   - Кожного разу при монтуванні додавався б новий слухач подій. Без очищення вони накопичуються в пам'яті (Memory Leak), що з часом призведе до сповільнення браузера, некоректної роботи та можливого "падіння" сторінки через надмірне споживання ресурсів.

5. **Порівняйте між собою HOC (Higher-Order Component) та Custom Hooks. Яку спільну архітектурну проблему вони вирішують і чому індустрія відмовилася від масового застосування HOC на користь кастомних хуків?**
   - Обидва підходи вирішують проблему **перевикористання логіки** між компонентами. Проте HOC створюють "пекло обгорток" (wrapper hell), ускладнюють передачу пропсів та дерево компонентів. Хуки дозволяють використовувати ту саму логіку всередині компонента без зміни його структури, вони легші для тестування та розуміння.
